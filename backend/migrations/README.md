# 마이그레이션 — 적용된 파일은 고치지 않는다

`backend/migrations/*.sql` 는 `sqlx::migrate!` 가 기동 시 적용하는 순서 있는 목록이다.
sqlx 는 적용한 각 파일의 **체크섬을 `_sqlx_migrations` 에 함께 기록**하고, 다음 기동 때
파일이 그 체크섬과 다르면 마이그레이션을 진행하지 않고 **프로세스를 세운다**:

```
migration 4 was previously applied but has been modified
```

## 왜 이 파일이 있는가

2026-09-02, 이미 적용된 `0004_analysis_stages.sql` 의 **주석 한 줄**을 고친 변경이 머지됐다.
SQL 은 한 글자도 바뀌지 않았지만 체크섬은 파일 전체에 대한 것이라 값이 달라졌고, 새 이미지가
롤아웃되자 API 가 기동에 실패했다. 데이터베이스에는 이미 4번이 적용돼 있었기 때문이다.
프로덕션이 **6시간 41분** 죽었다.

되돌리는 방법은 파일을 **바이트 단위로 원상 복구**하는 것뿐이었다(PR #42). 그래서 지금
`0004_analysis_stages.sql` 에는 **삭제된 목업 `docs/mockups/s04-analysis-progress.html` 을
가리키는 주석**이 남아 있다 — 그것은 방치가 아니라 **의도된 되돌림**이다. 고치지 말 것.

## 규칙

1. **이미 배포에 적용된 마이그레이션 파일은 어떤 이유로도 편집하지 않는다.** 오타·주석·공백·
   줄바꿈 전부 포함이다. 체크섬은 SQL 이 아니라 **파일**에 걸린다.
2. 스키마를 바꿔야 하면 **다음 번호의 새 파일**을 만든다.
3. 아직 어디에도 적용되지 않은 마이그레이션(같은 PR 안에서 방금 추가한 것)만 자유롭게 고칠 수
   있다. 이 경우 아래 `tests/migrations.rs` 의 고정 체크섬도 같은 커밋에서 갱신한다.
4. 파일 안의 주석이 레포의 다른 파일을 가리키고 그 파일이 나중에 사라지더라도, **주석을 고쳐
   맞추지 않는다.** 마이그레이션은 그것이 적용된 시점의 기록이다.

## 무엇이 이 규칙을 지키는가

`backend/tests/migrations.rs` 의 `applied_migrations_are_never_edited` 가 각 파일의 SHA-256 을
고정해 둔다. 적용된 파일이 바뀌면 **PR 단계에서** 붉어진다 — 이 검사가 없으면 위반은 머지되고,
이미지 핀이 반영돼 새 파드가 뜨는 순간에야 드러난다(그때는 이미 장애다).

새 마이그레이션을 더할 때는 그 테스트의 목록에 파일명과 체크섬을 한 줄 더한다. 값은:

```bash
sha256sum backend/migrations/00NN_*.sql
```
