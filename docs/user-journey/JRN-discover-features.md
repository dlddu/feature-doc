## 1. 서비스 개요 (참고)

[`values.md`](../values.md) 참조. 이 여정은 제품의 핵심 파이프라인(횡단 분석 → 탐색 전략 → 후보 추출)이 사용자에게 어떻게 보이는지를 다룬다.

## 2. 여정 정의

**대상 사용자 (페르소나)**
Pre (P1). P2는 이 여정에 들어오지 않는다 — 후보 승인·거부는 저장소 소유자의 결정이다.

**진입 맥락**
[`JRN-connect-repo`](./JRN-connect-repo.md)를 막 끝내고 분석이 백그라운드에서 돌기 시작한 상태. 사용자는 앱을 닫고 다른 일을 하고 있다.

**트리거**
단계 완료 푸시 알림. 알림이 꺼져 있다면 사용자가 스스로 앱을 다시 여는 순간.

**사용자 목표**
자기 코드베이스에서 **최종 사용자에게 노출되는 기능이 무엇인지**의 목록을, 자기가 납득하는 형태로 확정하는 것.

**완료 기준**
추출된 후보 전부에 대해 승인/거부 결정이 끝나 확정 feature 목록이 생성됨. (로그로 확인 가능: 미결정 후보 0건 + `features` 레코드 생성)

> 이 여정의 특징은 **사용자가 능동적으로 머물지 않는다**는 것이다. 분석은 분 단위로 길고, 사용자는 나갔다 돌아온다. 화면은 (a) 떠나 있는 동안 진행이 살아 있음을 보이고 (b) 돌아올 이유를 만들어야 한다.

## 3. 단계별 상세

### `STP-leave-and-return` 맡겨두고 떠났다가 돌아오기

- **사용자 행동**: 앱을 닫고 다른 일을 한다. 알림을 받고 다시 열어 진행률·누적 비용을 확인한다. 실패한 단계가 있으면 그 단계만 재시도한다
- **터치포인트**: 푸시 알림, S04 분석 진행
- **생각·감정**: "돌려놓고 잊고 있었는데 잘 되고 있나" — 알림 없이 한 시간이 비면 *실패한 것 같은* 불안이 생긴다
- **페인포인트 / 이탈 위험**: 한 단계가 실패했을 때 처음부터 다시 돌리게 하면, 다시 시작을 거는 심리적 비용이 급격히 커진다(F3) → 단계별 재시도. 앱을 닫았다 열어도 진행 상태가 그대로 복원될 것. 누적 비용이 항상 보일 것
- **연결 AC**: AC1.5, AC4.6

### `STP-review-landscape` 내 코드가 무엇 위에 서 있는지 확인하기

- **사용자 행동**: 추출된 횡단 관심사(인프라·저장소 구조·아키텍처·프레임워크·미들웨어)를 카테고리별로 훑고, 항목마다 붙은 코드 근거를 확인한다
- **터치포인트**: S05 횡단 관심사
- **생각·감정**: "내 코드를 남이 정리해준 건 처음 보네" — 익숙한 구조를 외부의 눈으로 보는 첫 경험. 동시에 *누락이 있으면 즉시 잡아낸다*
- **페인포인트 / 이탈 위험**: LLM 비결정성으로 재분석마다 결과가 흔들리면 신뢰가 무너진다(F4) → 같은 커밋 재분석 시 결과가 결정적이거나, 다르면 **무엇이 다른지**가 항목별로 명시된다. 근거 없는 항목은 표시하지 않거나 "근거 없음"으로 명시
- **연결 AC**: AC1.2

### `STP-tune-strategy` 내가 아는 코드 구조를 전략에 보태기

- **사용자 행동**: LLM이 만든 탐색 전략(진입점 패턴·라우팅 위치·UI 컴포넌트 경로·API 엔드포인트·CLI 등)을 항목별로 검토하고, 자기만 아는 비표준 진입점을 추가하거나 틀린 항목을 지운 뒤 승인한다
- **터치포인트**: S06 탐색 전략 검토
- **생각·감정**: "우리는 admin CLI가 따로 있는데 그건 안 잡혔네" — 자기 코드를 아는 사람만 보탤 수 있는 한 줄
- **페인포인트 / 이탈 위험**: 전략의 영향력을 사용자가 모르고 그냥 넘기면, 다음 단계 후보 목록의 품질이 조용히 나빠진다 → 이 화면이 **최종 목록 품질을 결정하는 첫 게이트**임을 화면에서 알리고, 승인 전 전략은 다음 단계 입력으로 절대 쓰이지 않게 한다. 사용자 편집은 다음 분석에서 참조되도록 보존
- **연결 AC**: AC1.3

### `STP-sift-candidates` 진짜 기능과 아닌 것 가르기

- **사용자 행동**: 후보별 발견 위치와 추정 근거를 확인하고 승인/거부/병합/이름 변경한다. 거부에는 사유를 적는다
- **터치포인트**: S07 feature 후보 검토
- **생각·감정**: "이건 디버그용이지 사용자 기능이 아닌데" — 자기 코드라서 내부 도구를 빠르게 식별한다
- **페인포인트 / 이탈 위험**: 후보가 수십 개면 모바일에서 한 세션에 끝나지 않아 절반만 결정한 채 방치된다 → 부분 결정 상태를 저장하고 남은 개수를 보여 다음 세션에서 이어가게 한다. 거부 사유를 대충 적으면 재분석 때 같은 판단을 반복해야 하므로(F7의 원인), 사유 입력에 예시를 제공
- **연결 AC**: AC1.4

### `STP-add-missing` 빠진 기능 직접 추가하기

- **사용자 행동**: 목록을 보고 "이건 왜 없지" 싶은 기능을 자연어로 직접 추가한다. LLM이 코드를 뒤져 인수 기준 초안과 의존성 후보를 제안하면 확정한다
- **터치포인트**: S07 feature 후보 검토(추가 진입점 — 목업·와이어프레임 미표현)
- **생각·감정**: "자동으로는 못 잡았지만 이건 분명히 사용자 기능이야"
- **페인포인트 / 이탈 위험**: 코드에서 근거를 못 찾았는데도 그럴듯한 초안을 만들어내면 V1(코드 근거)이 무너진다 → 근거를 못 찾으면 **"근거 없음"을 명시하고 강제로 만들어내지 않는다**. 이 단계의 진입점이 화면에 없으면 사용자는 기능이 없다고 생각한다
- **연결 AC**: AC3.2

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 특정 분석 단계 실패 | 전체 파이프라인을 죽이지 않고 그 단계만 재시도 | `STP-leave-and-return` |
| 앱 종료 후 복귀 | 진행 상태·누적 비용이 그대로 보존되어 동일 진행률로 복원 | `STP-leave-and-return` |
| 횡단 분석 결과를 사용자가 수정하고 싶을 때 | 이 단계에서는 직접 편집이 없다. 인지만 하고 전략 단계에서 보정 | `STP-tune-strategy` |
| 이전에 거부했던 후보가 다시 잡힘 | "이전에 거부된 항목입니다 + 거부 사유" 표시, 자동 채택하지 않음 | `STP-sift-candidates` |
| 후보를 절반만 결정한 채 이탈 | 결정 상태 저장, 남은 개수를 홈에 표시하고 이어하기 제공 | `STP-sift-candidates` |
| 추가하려는 기능의 코드 근거를 못 찾음 | "근거 없음"으로 명시한 채 추가하거나 취소 | `STP-add-missing` |
| 누적 비용이 사용자 예상을 크게 초과 | 비용을 계속 노출하고 중단 경로 제공 | 여정 중단 |
