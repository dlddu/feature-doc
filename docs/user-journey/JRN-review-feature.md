## 2. 여정 정의

**대상 사용자 (페르소나)**
Pre (P1) — 저장소 소유자. 코드 근거가 진짜인지 판단할 수 있는 유일한 사람이다. 같은 화면을 P2도 보지만 목적이 다르므로 [`JRN-understand-feature`](./JRN-understand-feature.md)로 분리했다.

**진입 맥락**
[`JRN-discover-features`](./JRN-discover-features.md)에서 feature 목록을 확정한 직후, 또는 나중에 특정 기능의 문서가 미심쩍어서 다시 들어옴. 자동으로 진입하지 않고 **사용자가 기능 하나를 골라 들어가는 능동 행동**이 필요하다.

**트리거**
확정 목록이 생겼다는 사실 자체, 또는 "이 기능 설명이 좀 이상한데"라는 자각.

**사용자 목표**
기능 하나의 인수 시나리오가 실제 코드 동작과 맞는지 확인하고, 틀렸거나 모호하면 고쳐 두는 것.

**완료 기준**
그 feature의 시나리오와 의존성을 확인하고, 수정이 필요했다면 diff 승인/거부까지 마침. (로그로 확인 가능: feature 조회 이벤트 + 편집 제안이 있었다면 승인/거부 결정 레코드)

> 이 여정은 12개 feature가 있으면 **12번 반복된다**. 한 번의 진입이 짧고 반복 가능해야 하며, 절반만 처리하고 나가도 다음에 이어갈 수 있어야 한다.

## 3. 단계별 상세

### `STP-read-scenarios` 사용자에게 무슨 일이 벌어지는지 읽기

- **사용자 행동**: Given-When-Then 형태의 인수 시나리오를 위에서 아래로 읽는다. "코드와 테스트가 다르게 말하는 부분" 섹션이 있으면 따로 확인한다
- **터치포인트**: S08 인수 시나리오
- **생각·감정**: "내가 만든 기능이 이렇게 설명되는구나" — 표현이 자기 이해와 어긋나면 즉시 걸린다
- **페인포인트 / 이탈 위험**: 시나리오에 개발자 용어(`POST /api/v1/...` 등)가 남아 있으면 V3가 무너지고, 이 문서를 P2에게 공유할 수 없게 된다(F5) → 비개발자가 읽고 그 기능을 설명할 수 있는지가 검수 기준선. 로직과 테스트가 모순되면 본 시나리오에 섞지 말고 별도 섹션으로 분리
- **연결 AC**: AC2.1, AC2.2, AC2.3

### `STP-verify-evidence` 근거 코드가 진짜 출처인지 확인하기

- **사용자 행동**: 각 시나리오에 달린 코드 근거 링크를 눌러 실제로 그 위치에서 나온 서술인지 확인한다
- **터치포인트**: S08 인수 시나리오(근거 링크)
- **생각·감정**: "그럴듯하게 썼는데 진짜 이 코드에서 나온 게 맞나?" — LLM 산출물에 대한 건강한 의심
- **페인포인트 / 이탈 위험**: 근거 링크가 모바일에서 확인하기 번거로우면(외부 이동, 큰 파일 통째 열림) 검수 자체를 건너뛰고 신뢰만으로 넘어가게 된다 → 근거는 파일·심볼 단위로 좁혀 보여주고, 확인 후 원래 자리로 돌아오는 경로를 유지
- **연결 AC**: AC2.1, AC2.2

### `STP-trace-dependencies` 이 기능이 무엇에 기대고 있는지 보기

- **사용자 행동**: 의존성 그래프를 훑고, 7종 카테고리(인프라·데이터·아키텍처·프레임워크·미들웨어·로직·인터페이스)별 목록을 펼쳐 근거를 확인한다
- **터치포인트**: S09 종단 의존성
- **생각·감정**: "알고는 있었는데 한 자리에서 본 적은 없었네" — V5를 처음 체감하는 순간
- **페인포인트 / 이탈 위험**: 그래프가 모바일에서 읽히지 않으면 카테고리 목록만 쓰이고 그래프는 죽은 UI가 된다 → 좁은 화면에서는 카테고리 목록을 기본으로, 그래프는 확장 보기로. 의존성이 텍스트가 아니라 구조화 데이터로 저장되어야 역방향 질의("이 데이터 모델을 쓰는 기능 전부")가 가능해진다
- **연결 AC**: AC2.4, AC2.5

### `STP-request-edit` 어색한 표현을 자연어로 고쳐달라 하기

- **사용자 행동**: "이 시나리오 더 명확하게", "에러 케이스 추가" 같은 한 줄을 입력한다
- **터치포인트**: S10 LLM 보조 편집
- **생각·감정**: "직접 쓰기는 귀찮고, 뭐가 문제인지는 알겠어"
- **페인포인트 / 이탈 위험**: 입력까지 가는 길이 길면 "직접 쓰는 게 빠르겠다"가 되어 이 기능이 죽는다(F8) → 시나리오를 읽던 자리에서 바로 요청할 수 있어야 한다. 거부했던 제안 패턴은 기록해 같은 제안을 반복하지 않는다
- **연결 AC**: AC3.1

### `STP-decide-diff` 제안된 변경을 승인하거나 버리기

- **사용자 행동**: LLM이 제시한 diff를 읽고 승인 또는 거부한다
- **터치포인트**: S10 LLM 보조 편집(diff 영역)
- **생각·감정**: "이 정도면 됐다" 또는 "내가 말한 건 이게 아닌데"
- **페인포인트 / 이탈 위험**: "요청 → diff 확인 → 승인/거부"가 3탭을 넘기면 모바일에서 쓰이지 않는다(F8) → 키보드 노출·모달 중첩·스크롤 깊이를 3탭 기준으로 검수. 승인 없이 적용되는 경로는 존재하지 않는다. 모든 변경은 출처(자동 / 사용자 by LLM / 사용자 직접)와 함께 이력에 남는다
- **연결 AC**: AC3.1, AC3.4, AC4.4

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 로직과 테스트가 모순 | 본 시나리오와 분리된 별도 섹션으로 표시하고 사용자 판단에 맡김 | `STP-read-scenarios` |
| 표현이 아니라 발견 자체가 잘못됨 | 이 여정이 아니라 후보 결정으로 돌아가야 함 | [`JRN-discover-features`](./JRN-discover-features.md) `STP-sift-candidates` |
| LLM 제안이 요청과 어긋남 | 거부하고 다시 요청. 거부된 제안은 기록되어 다음 제안에서 회피 | `STP-request-edit` |
| 검수 도중 이탈 | 읽던 feature와 위치를 보존하고 다음 진입 시 이어하기 | `STP-read-scenarios` |
| 의존성 근거가 비어 있음 | "근거 없음"으로 명시. 임의로 채우지 않음 | `STP-trace-dependencies` |
| 12개 중 1~2개만 처리하고 종료 | 정상 흐름. 미검수 feature 개수를 목록에 표시 | 여정 재진입 |
