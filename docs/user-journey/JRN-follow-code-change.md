## 1. 서비스 개요 (참고)

[`values.md`](../values.md) 참조. 이 여정은 V4("문서는 코드 변경에 뒤처지지 않는다")가 실제로 지켜지는지 사용자가 확인하는 자리다.

## 2. 여정 정의

**대상 사용자 (페르소나)**
Pre (P1). P2는 diff 요약 알림을 받고 필요한 항목만 확인할 뿐, 충돌의 최종 결정권은 갖지 않는다.

**진입 맥락**
첫 분석과 검수가 끝난 지 며칠~몇 주 지난 시점. 사용자는 그동안 평소대로 코드를 작성했고, FeatureDoc을 잊고 있었다.

**트리거**
코드 push(또는 새 커밋, 명시적 재분석 요청) 이후 도착한 "N개 기능의 표현이 갱신됐어요" 알림.

**사용자 목표**
이번 코드 변경이 **어느 기능의 무엇을 바꿨는지** 파악하고, 자동 결과와 자기가 손봤던 편집이 부딪히는 지점을 자기 뜻대로 정리하는 것.

**완료 기준**
변경된 feature 전부에 대해 diff를 확인하고, 미해소 충돌이 0건이 됨. (로그로 확인 가능: 충돌 상태 레코드 전부 해소 + 결정 이력 생성)

> 이 여정의 약속 한 줄: **자동 분석은 사용자의 명시적 결정 없이 사용자 편집을 절대 덮어쓰지 않는다.** 이 약속이 한 번이라도 깨지면 사용자는 [`JRN-review-feature`](./JRN-review-feature.md)의 편집 기능을 다시 쓰지 않는다.

## 3. 단계별 상세

### `STP-notice-change` 무엇이 바뀌었는지 알기

- **사용자 행동**: 알림을 열어 이번 재분석이 몇 개 기능을 건드렸는지, 충돌이 있는지 확인한다
- **터치포인트**: 푸시 알림, 분석 진행(재분석 상태)
- **생각·감정**: "내가 push한 게 문서에 반영됐나" — 반영 자체보다 *내가 손댄 게 살아 있나*가 더 신경 쓰인다
- **페인포인트 / 이탈 위험**: 알림이 "분석이 완료되었습니다"처럼 내용 없이 오면 열어볼 이유가 없어 방치된다 → 변경된 기능 수와 충돌 유무를 알림 본문에 담는다. 변경이 없으면 알림을 보내지 않는다
- **연결 AC**: AC2.6

### `STP-scan-diff` 어느 기능의 무엇이 달라졌는지 훑기

- **사용자 행동**: 변경된 기능 목록을 훑고, 각 기능의 이전 버전 대비 diff(달라진 시나리오, 추가·제거된 의존성)를 본다
- **터치포인트**: 후보 목록(변경 표시), 인수 시나리오(diff), 종단 의존성(diff)
- **생각·감정**: "내가 의도한 대로 반영됐네" 또는 "왜 이게 바뀌었지?" — 후자가 나오면 코드 리뷰의 신호로도 쓰인다
- **페인포인트 / 이탈 위험**: 변경되지 않은 기능까지 갱신된 것처럼 보이면 diff를 신뢰하지 않게 된다 → 변경 없는 feature는 그대로 유지하고 표시도 하지 않는다. 의존성 변화는 시나리오 변화와 나란히 보여야 영향 범위가 한 번에 읽힌다
- **연결 AC**: AC2.6

### `STP-resolve-conflict` 내 편집과 자동 결과 중 무엇을 살릴지 정하기

- **사용자 행동**: 충돌 배너에서 자기 편집과 자동 결과를 비교하고, ① 자동 결과 채택 ② 편집 유지 ③ LLM 보조 병합 중 하나를 고른다. 병합을 골랐다면 병합 diff를 승인한다
- **터치포인트**: 인수 시나리오(충돌 배너), LLM 보조 편집(병합 diff)
- **생각·감정**: "내가 추가했던 건 살리고, 자동이 잡아낸 새 규칙만 얹고 싶다" — 대개 양자택일이 아니라 병합을 원한다
- **페인포인트 / 이탈 위험**: 자동 결과가 편집을 한 번이라도 덮어쓰면 편집 기능 전체가 죽는다(F6) → 충돌 검출은 **과하게 잡는 쪽이 안전**하다. 결정 옵션은 항상 3개를 유지하고, 미해소 충돌은 명확히 표시된 채 다음 재분석에서도 유지된다
- **연결 AC**: AC3.5

### `STP-recheck-candidates` 후보 목록의 변화 확인하기

- **사용자 행동**: 새로 잡힌 후보를 승인/거부하고, 예전에 거부했던 항목이 다시 올라왔으면 같은 결정을 유지하거나 이번엔 채택한다
- **터치포인트**: feature 후보 검토(재진입, "이전에 거부된 항목" 표시)
- **생각·감정**: "이거 지난번에도 거부했는데 또 나왔네" — 사유가 함께 보이면 3초 만에 끝나고, 안 보이면 처음부터 다시 판단해야 한다
- **페인포인트 / 이탈 위험**: 거부 사유가 보존되지 않으면 매 재분석마다 같은 판단을 반복하게 되어 재분석 자체가 부담이 된다(F7) → 거부 사유를 함께 노출하고 자동 채택하지 않는다. 삭제된 feature는 즉시 영구 삭제하지 않고 일정 기간 복구 가능한 상태로 둔다
- **연결 AC**: AC1.4, AC3.3

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 변경 사항 없음 | 알림을 보내지 않고 문서를 그대로 유지 | 여정 미진입 |
| 충돌 없이 자동 갱신만 발생 | diff 확인만으로 여정 완료 | `STP-scan-diff` 후 종료 |
| 충돌을 결정하지 않고 이탈 | 미해소 상태로 명확히 표시하고 다음 재분석에서도 유지 | `STP-resolve-conflict` |
| 병합 결과가 마음에 안 듦 | 병합 diff 거부 후 ①/② 재선택 | `STP-resolve-conflict` |
| 자동 갱신 결과가 명백히 틀림 | 이력에서 이전 시점으로 복원 | [`JRN-restore-history`](./JRN-restore-history.md) |
| 거부했던 항목을 이번엔 채택 | 사유를 갱신하고 확정 목록에 편입, 표현 검수로 이동 | [`JRN-review-feature`](./JRN-review-feature.md) `STP-read-scenarios` |
| 재분석 중 단계 실패 | 해당 단계만 재시도 (AC1.5) | `STP-notice-change` |
