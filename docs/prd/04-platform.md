# PRD: 플랫폼 (k8s · 자격증명 · 모바일 우선)

> 요구사항 #11, #12, #13을 묶은 PRD.
> 핵심 기능 PRD(분석/표현/문서 관리) 모두가 동작하기 위한 비기능적 토대를 정의한다.

## 달성 가치
- **V6: 사용자가 통제하는 자격증명·비용** — GitHub App 설치(저장소 접근 범위) / LLM API Key 관리.
- **V7: 모바일에서 즉시 검토·수정 가능** — UX의 기본 전제.
- **V8: 운영 환경에서의 안정적 가용성** — k8s 운영.

## 범위 / 비범위
- **범위**: GitHub OAuth 기반 사용자 본인 인증·세션·계정, 자격증명 등록·저장·사용·폐기, 접근 권한 없는 저장소 링크에서의 공유 요청 경로, 모바일 우선 UX 원칙, k8s 배포·확장성·관측 가능성.
- **비범위**: GitHub 외 인증 수단(SSO/이메일/자체 계정 등), 결제(사용자 LLM 비용은 사용자 키로 직접 발생).

## Acceptance Criteria

### AC4.1: GitHub App 설치를 통한 저장소 접근 연결·변경·해제
- **설명**: 사용자는 FeatureDoc GitHub App을 자신의 계정 또는 조직에 설치하고, 분석을 허용할 저장소를 선택할 수 있다. App은 분석에 필요한 최소 권한(저장소 콘텐츠 읽기·메타데이터 읽기)만 요청하며, 설치 전에 그 권한 범위를 사용자에게 안내한다. 시스템은 장기 사용자 비밀을 보관하지 않고, 호출 시점에 단기 설치 액세스 토큰(installation access token)을 발급해 사용한다. 사용자는 언제든 저장소 선택 범위를 변경하거나 App 설치를 해제할 수 있다.
- **달성 가치**: V6
- **검증 방법**: 발급되는 설치 액세스 토큰은 단기 만료되며 저장소 측에서 평문 형태로 조회 불가. App 설치 해제 또는 저장소 접근 범위 축소 시 진행 중 분석 작업도 명시된 정책에 따라 처리(중단/현재 호출까지만 완료)된다.

### AC4.2: 사용자 LLM API Key 등록·교체·폐기 및 호출 위임
- **설명**: 사용자는 자신의 LLM 제공자 API Key를 등록할 수 있고, 시스템은 모든 LLM 호출을 해당 키로 수행한다. 키는 평문 저장되지 않으며, 사용자는 호출 누적 횟수/추정 비용을 확인할 수 있다.
- **지원 제공자 범위**: 등록 대상은 **시스템이 분석 호출을 실제로 수행할 수 있는 제공자**로 한정한다. 호출이 아직 구현되지 않은 제공자의 키 등록 요청은 그 사유와 대안을 밝히며 거부되고, 키는 저장되지 않는다. 지원 범위는 호출 구현이 늘어날 때 함께 넓어지며, 별도의 목록으로 관리되지 않는다. 이 한정은 두 가지를 지킨다 — (a) 사용자는 **분석을 시작하기 전에**, 아직 아무 자격증명도 맡기지 않은 시점에 지원 여부를 안다. (b) 쓸 수 없는 키가 "이 분석이 쓸 키"로 선택되어 이미 동작하던 분석을 중단시키는 일이 생기지 않는다.
- **달성 가치**: V6
- **검증 방법**: 키 폐기 시 신규 LLM 호출이 차단됨. 사용자는 분석 작업 시작 전에 예상 호출 규모를 안내받는다. 미지원 제공자의 키 등록 요청은 거부되고 저장되지 않으며, 지원 여부의 판정은 실제 호출 구현과 한 곳에서 파생되어 둘이 어긋날 수 없다.

### AC4.3: 자격증명의 안전한 사용 정책
- **설명**: 자격증명(GitHub App 개인 키, 단기 설치 액세스 토큰, LLM API Key)은 (a) 저장 시 암호화, (b) 메모리상에서도 필요한 호출 직전에만 복호화, (c) 로그/오류 메시지에 출력 금지의 원칙을 따른다. 자격증명을 다루는 코드 경로는 감사 가능하도록 기록된다.
- **달성 가치**: V6, V8
- **검증 방법**: 시스템 로그에 토큰/키가 노출되지 않음을 검증. 키 사용 이력은 사용자가 조회 가능.

### AC4.4: 모바일 우선 UI/UX
- **설명**: 주요 화면(분석 진행 상황, feature 목록, 인수 테스트 검토, LLM 보조 수정, 의존성 조회)은 모바일 폭(예: 360–430px)에서 1차로 설계되며, 한 손 조작과 짧은 세션을 가정한다. 긴 분석 결과는 단계적으로 노출(요약 → 상세)된다.
- **달성 가치**: V7
- **검증 방법**: 주요 작업이 모바일 환경에서 1세션 5분 이내에 완료 가능. 데스크톱은 동일 화면을 확장 적용한다.

### AC4.5: k8s 배포 및 워크로드 분리
- **설명**: 시스템은 k8s에서 동작하며, (a) 사용자 요청을 받는 API 워크로드와 (b) 분석을 수행하는 백그라운드 워커 워크로드를 분리한다. 분석 작업은 큐를 통해 비동기로 실행된다.
- **달성 가치**: V8
- **검증 방법**: 워커가 다운되어도 API는 응답 가능. 워커는 수평 확장 가능.

### AC4.6: 관측 가능성과 비용 가시성
- **설명**: 분석 단계별 소요 시간, LLM 호출 횟수/토큰 사용량, 실패율이 운영자가 볼 수 있는 형태로 기록된다. 사용자에게도 본인 작업 기준의 누적 호출/추정 비용이 노출된다.
- **달성 가치**: V8, V6
- **검증 방법**: 임의 사용자의 임의 분석 작업의 단계별 비용을 운영자/사용자 모두가 추적 가능.

### AC4.7: 분석 작업의 격리
- **설명**: 한 사용자의 자격증명/저장소/분석 결과는 다른 사용자의 작업에서 접근 불가. 분석 워커는 사용자 단위로 격리되어 실행된다.
- **달성 가치**: V6, V8
- **검증 방법**: 권한 우회 시나리오 테스트에서 다른 사용자 데이터 접근 불가 확인.

### AC4.8: GitHub OAuth 기반 사용자 본인 인증과 세션
- **설명**: 사용자는 GitHub OAuth로 로그인해 본인을 식별한다. 로그인 성공 시 시스템은 사용자 계정을 생성·갱신(upsert)하고 서버 측 세션을 열어 만료가 있는 HttpOnly 쿠키로만 유지하며, 클라이언트에 장기 토큰을 노출하지 않는다. 미인증 상태에서는 보호된 API·화면에 접근할 수 없고 로그인으로 유도된다. 사용자는 언제든 로그아웃할 수 있으며, 로그아웃 시 해당 세션은 즉시 무효화된다. 이 인증은 AC4.3(사용자별 감사 이력)·AC4.6(사용자별 비용 가시성)·AC4.7(사용자별 격리)이 전제하는 '사용자' 식별의 기반이다.
- **달성 가치**: V6, V8
- **검증 방법**: 미인증 요청은 보호 API에서 거부된다. 로그인 후 본인 조회(예: `/api/me`)로 GitHub 계정 기준의 동일 사용자가 식별되고, 재로그인 시 계정이 중복 생성되지 않는다. 로그아웃 이후 이전 세션 쿠키로는 접근이 거부되며, 세션 토큰·OAuth 코드는 로그/오류 메시지에 평문 노출되지 않는다(AC4.3 원칙 준수).

### AC4.9: LLM 산출물의 출력 언어 사용자 설정
- **설명**: 사용자는 LLM이 작성하는 산출물 문장(이름·요약·설명·시나리오 등)을 받을 언어를 한국어 또는 영어 중에서 한 번 골라 둘 수 있다. 고른 적 없는 사용자는 한국어로 받는다. 설정은 분석을 시작하는 시점에 그 분석에 고정되어, 이후 설정을 바꿔도 진행 중인 분석은 한 언어로 끝까지 작성되고 변경은 다음에 시작하는 분석부터 적용된다. 파일 경로·코드 식별자·심볼·탐색 패턴처럼 다른 단계와 화면이 짝을 맞추는 값은 언어와 무관하게 원문 그대로 유지된다.
- **달성 가치**: V3, V6
- **검증 방법**: 설정은 사용자별로 저장되어 다른 사용자에게 영향을 주지 않고, 지원하지 않는 언어 값은 거부되며 기존 설정을 덮어쓰지 않는다. 분석이 시작 시점의 언어를 기록하고, 시작 후 설정을 바꿔도 그 분석의 모든 LLM 호출은 기록된 언어로 요청된다. 두 제공자(OpenAI·Anthropic) 모두 같은 언어 지시를 받는다.

### AC4.10: 접근 권한 없는 저장소 링크의 공유 요청 경로
- **설명**: 접근 권한이 없는 저장소의 링크를 연 사용자는 그 저장소를 목록에서도 상세에서도 볼 수 없으며(AC4.7), 막힌 그 자리에서 **소유자에게 공유를 요청하는 경로**를 안내받는다. 요청을 보내면 시스템은 요청이 접수되었음과 허락 시 요청자에게 알림이 간다는 것을 알리고, 허락이 오기 전까지 그 저장소는 여전히 목록·상세에 나오지 않는다. 요청 이후 그 자리에서 이어지는 경로는 다른 링크를 여는 것이다.
- **AC4.7과의 관계**: 이 경로는 AC4.7의 비확인 원칙을 깨지 않는다. 요청 접수의 응답과 화면은 대상이 실재하든 실재하지 않든 **서로 구분되지 않으며**, 소유자의 신원은 요청자의 화면·응답 어디에도 나타나지 않는다. 접근 허용 여부는 소유자가 AC4.1의 저장소 선택 범위로 정하는 것이고, 이 요청은 그 결정을 **재촉하는 통지일 뿐 우회 경로가 아니다**.
- **달성 가치**: V6
- **검증 방법**: 권한 없는 링크를 연 사용자의 화면에 공유 요청 경로가 나타나고, 요청 후 화면이 접수·통지 예고 상태로 바뀐다. 실재하는 남의 대상과 실재하지 않는 대상에 대한 요청의 응답·화면이 서로 구분되지 않는다. 허락 시 요청자에게 도달하는 알림은 그 통지 채널이 서는 시점에 함께 검증한다.

## AC 간 관계
- AC4.1~4.3은 자격증명 영역(V6).
- AC4.4는 UX 영역(V7).
- AC4.5~4.7은 운영 영역(V8).
- AC4.7은 V6 + V8 양쪽에 걸친 보안·운영 요구.
- AC4.9는 사용자 선호 영역(V3 + V6)으로, 산출물이 최종 사용자가 읽을 언어로 쓰이게 하며 그 선택을 사용자가 통제한다.
- AC4.8은 본인 인증 영역(V6 + V8)으로, AC4.3·AC4.6·AC4.7의 '사용자별' 요구가 전제하는 사용자 식별을 제공한다.
- AC4.10은 접근 요청 영역(V6)으로, AC4.7이 세운 비노출·비확인 위에서 소유자의 AC4.1 범위 결정을 재촉하는 경로만 제공한다 — 접근을 스스로 열지 않는다.
