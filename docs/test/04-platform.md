# 테스트 문서: 플랫폼 (k8s · 자격증명 · 모바일 우선)

## 검증 대상 AC
- AC4.1: GitHub App 설치를 통한 저장소 접근 연결·변경·해제 (PRD: 플랫폼)
- AC4.2: 사용자 LLM API Key 등록·교체·폐기 및 호출 위임 (PRD: 플랫폼)
- AC4.3: 자격증명의 안전한 사용 정책 (PRD: 플랫폼)
- AC4.4: 모바일 우선 UI/UX (PRD: 플랫폼)
- AC4.5: k8s 배포 및 워크로드 분리 (PRD: 플랫폼)
- AC4.6: 관측 가능성과 비용 가시성 (PRD: 플랫폼)
- AC4.7: 분석 작업의 격리 (PRD: 플랫폼)
- AC4.8: GitHub OAuth 기반 사용자 본인 인증과 세션 (PRD: 플랫폼)
- AC4.9: LLM 산출물의 출력 언어 사용자 설정 (PRD: 플랫폼)
- AC4.10: 접근 권한 없는 저장소 링크의 공유 요청 경로 (PRD: 플랫폼)

## 테스트 시나리오

### 시나리오 1: GitHub App 설치와 권한 범위 안내
- **사전 조건**: App 미설치 상태.
- **실행 단계**: GitHub App 연결 화면 진입 → 요청 권한 범위(콘텐츠·메타데이터 읽기) 확인 → GitHub 설치 페이지로 이동 → 접근을 허용할 저장소 선택 → 설치 완료 후 앱으로 복귀
- **기대 결과**: 설치 전에 App이 요청하는 최소 권한 범위가 표시된다. 설치 후 어떤 저장소에 접근이 허용됐는지 표시되며, 장기 사용자 비밀은 어디에도 저장되지 않는다.
- **검증 AC**: AC4.1, AC4.3

### 시나리오 2: 진행 중 분석 도중 App 설치 해제
- **사전 조건**: 분석 1건이 진행 중.
- **실행 단계**: App 설치 해제(또는 해당 저장소의 접근 범위 제거) → 진행 상황 확인
- **기대 결과**: 사전 명시된 정책에 따라 분석이 중단되거나 현재 호출까지만 마무리된다. 그 결과가 사용자에게 통지된다.
- **검증 AC**: AC4.1

### 시나리오 3: LLM API Key 등록 후 호출 위임
- **사전 조건**: 키 없음.
- **실행 단계**: 키 등록 → 임의 분석 트리거 → LLM 제공자 측 호출 로그 확인
- **기대 결과**: 모든 LLM 호출이 사용자 키로 발생한다. 시스템 측 키는 사용되지 않는다.
- **검증 AC**: AC4.2

### 시나리오 4: 키 폐기 후 신규 호출 차단
- **사전 조건**: 키 등록 상태에서 분석 진행 중.
- **실행 단계**: 키 폐기 → 새 분석 트리거 시도
- **기대 결과**: 신규 LLM 호출이 차단되며, "키가 없거나 폐기되었습니다" 메시지가 표시된다.
- **검증 AC**: AC4.2

### 시나리오 5: 자격증명의 로그 노출 검증
- **사전 조건**: App이 설치되고 LLM API Key가 등록된 상태에서 정상 분석 1회 + 의도적 오류 1회 유발.
- **실행 단계**: 시스템 로그/에러 리포트 검사
- **기대 결과**: 어떤 로그/오류 메시지에서도 설치 액세스 토큰·API Key의 평문이나 그 일부가 노출되지 않는다.
- **검증 AC**: AC4.3

### 시나리오 6: 모바일 우선 UI 검증 (5분 세션)
- **사전 조건**: 분석이 완료되어 feature 목록과 인수 테스트가 존재.
- **실행 단계**: 모바일 폭(예: 390px) 환경에서 (a) 분석 진행 확인, (b) feature 1개 검토, (c) LLM 보조 수정 1회, (d) 의존성 1건 조회 — 5분 안에 수행
- **기대 결과**: 모든 작업이 한 손 조작과 5분 내에 완료 가능. 긴 결과는 요약 → 상세 단계 노출이 적용된다.
- **검증 AC**: AC4.4

### 시나리오 7: 워커 다운 시 API 가용성
- **사전 조건**: k8s에 API와 워커 워크로드가 분리되어 배포된 상태.
- **실행 단계**: 워커 파드 모두 강제 종료 → API에 대한 사용자 요청(자격증명 조회, 결과 조회) 시도
- **기대 결과**: API는 정상 응답하며, 신규 분석 요청은 큐에 적재되어 워커 복구 후 처리된다. 사용자에게 "분석 작업이 대기 중입니다" 표시.
- **검증 AC**: AC4.5

### 시나리오 8: 워커의 수평 확장
- **사전 조건**: 다수 분석 요청이 큐에 적재된 상태.
- **실행 단계**: 워커 replica를 늘림
- **기대 결과**: 처리량이 비례적으로 증가하고, API/워커 간 결합 없이 확장된다.
- **검증 AC**: AC4.5

### 시나리오 9: 사용자별 비용 가시성
- **사전 조건**: 한 사용자가 여러 분석을 수행.
- **실행 단계**: 사용자 화면에서 누적 LLM 호출 횟수와 토큰 사용량 확인
- **기대 결과**: 작업별·전체별 호출 횟수와 추정 비용이 표시된다. 운영자 화면에서도 동일한 데이터에 접근 가능.
- **검증 AC**: AC4.6

### 시나리오 10: 사용자 간 데이터 격리
- **사전 조건**: 사용자 A, B가 각각 다른 저장소를 분석한 상태.
- **실행 단계**: 사용자 A 인증으로 사용자 B의 자원(자격증명/저장소/feature 데이터)에 직접 API 호출 시도
- **기대 결과**: 모든 시도가 권한 거부로 차단된다. 워커 작업 컨텍스트도 사용자별로 격리되어 동일 워커 인스턴스에서 처리되어도 데이터가 섞이지 않는다.
- **검증 AC**: AC4.7

### 시나리오 11: 미인증 접근 차단과 GitHub 로그인
- **사전 조건**: 로그인하지 않은 상태.
- **실행 단계**: 보호된 화면/API(자격증명 조회 등) 접근 시도 → 로그인 유도 확인 → GitHub OAuth 로그인 수행 → 본인 정보 조회
- **기대 결과**: 미인증 접근은 거부되고 로그인으로 유도된다. 로그인 후 본인 조회에서 GitHub 계정 기준의 사용자가 식별되며, 동일 계정으로 재로그인해도 계정이 중복 생성되지 않는다.
- **검증 AC**: AC4.8

### 시나리오 12: 로그아웃 후 세션 무효화
- **사전 조건**: 로그인 상태(세션 쿠키 보유).
- **실행 단계**: 로그아웃 → 직전 세션 쿠키를 그대로 사용해 보호 API 재호출
- **기대 결과**: 로그아웃 즉시 해당 세션이 무효화되어 이전 세션 쿠키의 모든 요청이 거부된다. 세션 토큰은 로그/오류 메시지에 평문 노출되지 않는다.
- **검증 AC**: AC4.8, AC4.3

### 시나리오 13: 미지원 제공자의 키 등록 거부
> 시나리오 3·4와 같은 AC를 보지만 뒤에 붙인다 — 기존 번호가 다른 AC의 자동화·문서에 인용돼 있어 재배치하지 않는다.
- **사전 조건**: 로그인 상태. 분석 호출이 아직 구현되지 않은 제공자가 하나 이상 존재한다(현재: Google).
- **실행 단계**: 등록 화면에서 그 제공자를 선택 → 형식이 올바른 키를 입력 → 등록 시도 → 이어서 저장 상태와 활성 키를 확인
- **기대 결과**: 등록이 거부되고(HTTP 400) 그 사유와 대안 제공자가 화면에 표시된다. 키는 저장되지 않아 목록에 나타나지 않으며, 이미 등록돼 있던 지원 제공자의 키가 계속 "이 분석이 쓸 키"로 남는다(미지원 키가 최신이라는 이유로 그 자리를 빼앗지 않는다). 지원 여부의 판정은 실제 호출 구현에서 파생되므로, 호출이 없는 제공자가 등록 경로로 들어올 수 없다.
- **검증 AC**: AC4.2

### 시나리오 14: 출력 언어 설정과 분석 시점 고정
- **사전 조건**: 로그인 상태. GitHub App 설치와 LLM 키 등록을 마쳤고, 출력 언어를 고른 적이 없다.
- **실행 단계**: 키 등록 화면에서 출력 언어 기본값 확인 → English 선택 → 화면을 다시 열어 유지 확인 → 분석 시작 → 한국어로 다시 변경 → 방금 시작한 분석과 새로 시작한 분석의 언어 확인 → 지원하지 않는 언어 값으로 저장 시도
- **기대 결과**: 기본값은 한국어다. 선택은 누르는 즉시 저장되어 다시 열어도 유지된다. English일 때 시작한 분석은 이후 설정을 한국어로 바꿔도 English로 기록된 채 남고, 새로 시작한 분석은 한국어로 기록된다. 지원하지 않는 언어 값은 거부되고(HTTP 400) 저장된 설정은 바뀌지 않는다.
- **검증 AC**: AC4.9

### 시나리오 15: 접근 권한 없는 저장소의 공유 요청
- **사전 조건**: 사용자 A와 B가 각각 로그인 가능한 상태. A가 저장소 하나를 분석해 두었고, B에게는 그 저장소에 대한 접근 권한이 없다. B는 그 분석의 주소(공유 링크)를 받았다.
- **실행 단계**: B로 로그인 → 목록에서 그 저장소가 없음을 확인 → 받은 주소로 직접 진입 → 안내 화면의 공유 요청 경로 확인 → 요청 전송 → 화면 상태 확인. 대비군으로 **실재하지 않는 임의 id**의 주소에 같은 절차를 그대로 수행한다.
- **기대 결과**: 목록에도 상세에도 그 저장소가 나오지 않고, 안내 화면이 소유자에게 공유를 요청하는 경로를 제시한다. 요청 후 화면은 요청이 접수되었고 허락 시 알림이 간다는 것을 알리며, 그 자리에서 이어지는 경로는 다른 링크 열기뿐이다. 대비군과 응답·화면이 **서로 구분되지 않는다**(대상의 실재 여부가 새지 않는다). 소유자의 신원은 요청자의 화면·응답 어디에도 나타나지 않는다.
- **검증 AC**: AC4.10, AC4.7
