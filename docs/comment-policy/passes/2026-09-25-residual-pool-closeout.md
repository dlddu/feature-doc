## 왜 앞의 두 파일은 판정만 하는가

이 패스가 집는 두 파일은 **둘 다 판정기 `tools/check-data-format-change.py` 의 규칙에 걸리는
파일**이다 — `backend/migrations/0014_feature_doc_restores.sql` 은 D1, 판정기 자신은 D6.
두 규칙은 **그 PR 이 그 경로를 건드렸는가**로만 걸리므로(`classify()` 의 `f in SELF_PATHS` ·
`f.startswith("backend/migrations/")`), 주석을 한 글자라도 지우면 워크플로 `review — data format`
이 `review/manual-approval` status 를 **아예 붙이지 않고**, 그 status 는 `main` 룰셋의 필수
체크라 머지가 사람 서명 뒤로 간다.

**반면 판정 자체는 그 게이트를 지나지 않는다.** 원장에 행을 더하는 일은 `docs/` 만 건드리므로
판정기가 `✅ 해당 없음` 을 내고 status 가 자동으로 붙는다. 27차 패스(#150)가 D1 풀 5파일
123행을 **순 제거 0 · 유지 123** 으로 닫은 것이 같은 모양이고, 이 패스는 그 선례를 따른다.

두 몫을 「제거까지 한 덩어리」로 묶지 않는 이유는 원장이 이미 이름 붙인 실패 모양 때문이다 —
가벼운 쪽이 무거운 쪽의 운영 일정에 묶여 **영구 이월**된다. `tools/check-data-format-change.py`
36행은 2026-09-20 유입 이래, `0014` 33행은 09-25 유입 이래 **어느 판정도 받은 적이 없다**
(원장에 행 자체가 없었다). 판정을 먼저 착지시키면 그 뒤의 제거는 줄 번호까지 적힌 명세를
들고 각자의 게이트를 통과하면 된다.

## 복원 경로를 센 방법

③(PR 제목·본문·리뷰 코멘트)의 모집단은 **저작 PR 만** 세었다 — 그 주석 블록을 실제로 써 넣은
PR 이다. 판정 패스 PR(이 패스를 포함해 원장을 고치는 PR)이 「유지」를 설명하려 주석을 인용한
것은 ③ 히트가 아니다. 그것을 세면 정책이 지키라고 한 주석이 전부 제거 대상이 되는 자기
무효화 고리가 생긴다.

- `0014` 의 저작 PR = **#126**(슬라이스 6e, `9373c51`)
- `tools/check-data-format-change.py` 의 저작 PR = **#64**(신설 `b2724da`) · **#125**(D2~D5 제거
  `78183d2`) · **#127**(status 개명 `df5afd5`)

그리고 ③ 는 **서사를 닫지 가드를 닫지 않는다.** 이 레포의 저작 PR 본문은 설계 판단을 절 단위로
축자에 가깝게 적으므로 ③ 를 문면 일치만으로 적용하면 유지가 0 에 수렴한다. PR 본문은 **편집
지점에서 읽히지 않는다** — 「이 값이 무엇과 같아야 하는가 / 무엇을 넣지 말라 / 이 순서를 바꾸면
무엇이 조용히 깨지는가」를 말하는 줄은 본문과 겹쳐도 남긴다. 아래 두 표의 「판정」 칸이 그 구분을
줄 단위로 적용한 결과다.
