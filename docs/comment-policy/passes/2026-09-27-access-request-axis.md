## 「전건 제거」로 보이는 형태 셋을 부모 트리에서 세어 뒤집었다

첫 읽기에 제거로 기울었던 형태 셋이 **이미 판정을 받고 유지된 살아 있는 관례**였다. 판정 전에

| 형태 | 판정 완료 행에 살아 있는 줄 | 제거 선례 | 판정 |
|---|---|---|---|

정책 본문 1항은 「한 패스에서 마이그레이션 판정을 끝까지 모아 한 번의 repair 로 끝낸다」고
규정한다. 그 선결은 48차 창에서 **처음 충족됐다** — 48차가 `0016` 을 판정해 `0001`~`0016` 의
마이그레이션 판정이 전건 완료가 됐다. 그러나 그 판정보다 **먼저** 열린 47차 창(#193)은 자기
일곱 파일의 SHA-384 표를 이미 확정해 사람 게이트 앞에 서 있었고, 정책 5항이 그 표를 **머지 직전
재계산해 정확히 같은지** 대조하게 한다. 그 브랜치에 커밋을 얹으면 표가 달라져 5항의 대조가
깨지고 사람이 이미 계산한 값이 무효가 된다. 그래서 `0016` 은 #193 에 접어 넣지 않고 **자기 창**
으로 집행한다 — 위 「왜 「다음 repair 창」인가」가 등재한 그대로다.

**#193 은 2026-09-28T01:07:21Z 에 착지했고 그 창의 운영 DB repair 는 이미 끝났다**(version
**4·5·6·7·8·14·15** 일곱). 그래서 사람의 정비 창을 둘로 합치는 선택지는 사라졌고, 이 창이
**마이그레이션 축에 남은 마지막 repair** 다 — 아래 표의 **version 16 한 행**이 전부다.

🟢 **#193 의 repair 는 이 창의 값을 건드리지 않았다.** `0016_access_requests.sql` 은 #193 의 일곱
파일에 들어 있지 않아 새 main 에서도 바이트가 그대로이고(blob `cd57a4af` 부동), 부모 SHA-384 를
새 main `36416935` 에서 다시 계산해도 `d68d75b6…` 로 같다. 운영 DB 의 version 16 checksum 도
2026-09-28T00:52Z 관측에서 같은 값이었다 — 즉 아래 표의 「부모」 열은 소스와 운영 양쪽에서
확인된 값이다.

### repair 명세 — 사람이 하는 일

sqlx 는 `.sql` **파일 전체 바이트**의 SHA-384 를 `_sqlx_migrations.checksum` 에 들고 부팅마다
대조한다. 주석 한 글자만 달라도 `VersionMismatch` 로 **부팅이 실패**한다. CI 는 매번 새 DB 라
이 사고를 못 잡고, main 머지는 `pin` → Flux 롤아웃으로 사람 개입 없이 운영에 닿는다.

**표의 「새 SHA-384」가 운영 DB 에 들어가야 할 값이다.** 절차는
[`backend/migrations/README.md`](../../../backend/migrations/README.md) §「그래도 파일을 고쳐야
한다면 (repair)」 1~6단계를 **그대로** 따른다 — 여기 요약은 그 문서를 대체하지 않는다.

| version | 파일 | 부모(`36416935`)의 SHA-384 | **새 SHA-384 (UPDATE 할 값)** |
| ---: | --- | --- | --- |
| 16 | `0016_access_requests.sql` | `d68d75b6d087d19389281a1e5df81f2ccb3cf49f63974635656043959d216e24135070556b33676b4b04f2e21c4c344b` | `76015a82ca1c7303cefec9f453d188bfa2d2e45fc0ce4b429609a81f8f567e85cdc8b15b49e801ebe7862da01a944972` |

**version 16 하나뿐이다 — 다른 버전은 건드리지 않는다.** `backend/migrations/` 의 나머지
열다섯 파일은 이 PR 에서 바이트가 바뀌지 않았고, 그중 일곱(4·5·6·7·8·14·15)은 **#193 창에서
이미 repair 된 값**이라 다시 손대면 오히려 어긋난다.

> **「부모의 SHA-384」는 소스에서 계산한 값이지 운영 DB 를 관측한 값이 아니다.** README 가 같은
> 경고를 한다. 4단계에서 `SELECT version, description, hex(checksum) FROM _sqlx_migrations` 로
> **실제 값을 먼저 읽어** 이 열과 같은지 확인하고, 다르면 UPDATE 하지 말고 멈춘다 — 배포된
> 바이트가 여기 가정과 다르다는 뜻이다. `0016` 은 `13ffb8a`(2026-09-27) 착지분이라 그 이후에
> 롤아웃이 한 번이라도 돌았다면 행이 있고, 아직 적용된 적이 없으면 UPDATE 가 0행을 바꾸고
> 끝난다(그때는 애초에 repair 가 필요 없다 — README 4단계 마지막 문단).

순서 요약(자세한 명령은 README):

1. **DB 를 먼저 고치고 머지는 나중에.** 머지가 먼저면 새 파드는 무조건 `VersionMismatch` 로 죽는다.
2. `flux suspend kustomization <featuredoc-kustomization>` →
   `kubectl -n feature-doc scale deploy/featuredoc --replicas=0` →
   `rollout status` 로 파드가 **완전히 내려간 것 확인**(RWO 볼륨을 정비 파드가 잡아야 한다).
3. 정비 파드(`keinos/sqlite3:latest`, PVC `featuredoc-data` 마운트)에서
   `.bak` 백업 → 현재 `_sqlx_migrations` 확인 → **위 표의 version 16 만** UPDATE.
4. `flux resume kustomization <featuredoc-kustomization>` → **곧바로** 머지(resume 과 머지 사이가
   길면 구 이미지 파드가 새 체크섬과 어긋난 채 재기동될 수 있다).
5. `rollout status` 완료 · 부팅 로그에 `VersionMismatch` 없음 · `/hello` 응답 확인.
6. 실패하면 3에서 떠 둔 `.bak` 을 제자리에 복사하고 매니페스트의 이미지 태그를 직전 SHA 로
   되돌린다(이미지는 GHCR 에 이미 있으므로 재빌드 불필요).

**PR head 이미지를 쓰는 preview 환경이 기존 볼륨을 쓰는지**도 사람이 확인한다 — 쓴다면 그
환경의 파드도 repair 전 바이트로 부팅해 `VersionMismatch` 를 만들 수 있다.

**머지 직전 대조**: PR head 의 `0016_access_requests.sql` SHA-384 를 다시 계산해 위 표와
**정확히 같은지** 확인한다. 승인 뒤 rebase·수정으로 바이트가 달라졌으면 머지하지 않는다 —
운영 DB 는 이미 표의 값으로 고쳐져 있다.

```bash
python3 -c "import hashlib,pathlib; \
  p=pathlib.Path('backend/migrations/0016_access_requests.sql'); \
  print(hashlib.sha384(p.read_bytes()).hexdigest())"
```

### 걷은 좌표 — 원장 행 A 가 지목한 그대로

두 자리는 **줄 경계가 문장 경계와 맞지 않아** 절 단위로 끊었다(줄 수는 불변).

- `:17a` — 「… 않는다), 소유자는 같은 사람의 같은 요청을 여러 번 받지 않는다.」가 `UNIQUE`
  재진술의 꼬리이고, 같은 줄의 `:17b` 「재요청의 시각을」은 **유지 항의 머리**다. 절만 떼고
  유지 항을 문두로 올렸다.
- `:23` — 「… 지키기 어려워진다.」 뒤의 꼬리 절 「누구에게 알릴지는」이 제거 대상 `:24` 로
  이어진다. `:24` 만 걷으면 유지된 블록이 문장 중간에서 끊기므로 그 꼬리 절도 함께 끊었다.
  **행 A 가 이 꼬리를 따로 세지 않았다** — `:21-23` 을 유지로 적었을 때 셈은 줄 단위였고,
  절 단위로는 `:24` 의 주어가 `:23` 에 걸쳐 있다. 줄 수는 불변이므로 원장의 8행 기대값은
  그대로 닫힌다.

### `:17b-19` 구조형 재작성 — 담는 명제는 그대로

행 A 가 유지와 **함께 등재**한 항목이다(「`backend/migrations/README.md` §「시점 서술을 쓰지
않습니다」의 금지 예시와 같은 모양 ⇒ repair 창 집행에서 구조형으로 재작성, 줄 수 불변」).

- **전**: 「재요청의 시각을 따로 적지 않는 이유는 **지금** 그 값을 읽는 곳이 없기 때문이다 —
  통지 채널이 서는 슬라이스가 필요로 하면 **그때** 열을 늘린다.」
- **후**: 「재요청의 시각은 이 표의 어느 열에도 없고, 열거된 열에서 유도되지도 않는다. 그 값을
  읽는 쪽이 생기면 열을 더하는 마이그레이션이 필요하다 — 이 표만 보고 재요청 시각을 계산하려는
  코드는 조용히 틀린 값을 만든다.」

유지 근거(「부재는 네 복원 경로 어디로도 복원되지 않는다」)는 그대로 살아 있고, 바뀐 것은
「지금 / 그때」 시점 어법뿐이다. **재작성이 새 제거 후보를 만들지 않는지 확인했다** — 후행 문면은
`UNIQUE` 선언을 다시 말하지 않고(복원 경로 ① 무관), `docs/` 전수에 대응 문면이 없으며
(`재요청의 시각`·`requested_at` 이 `docs/` **0건** — 48차 실측과 같다. `requested_at` 은
`backend/` 에 3히트지만 전부 `feature_dependency_requests`·`feature_additions` **다른 표의 열**이라
이 표의 부재를 복원하지 않는다), 조용한 파손형 가드의 형태를 유지한다. 줄 수 3 불변.

### #193 착지 뒤의 재생 — 실측

이 PR 의 첫 판(head `c1b9b694`, base `5b753ff`)은 #193 이 먼저 착지하면서 `DIRTY` 가 됐다

새 main `36416935` 위에서 전건 성공으로 재생했고, 결과는:
